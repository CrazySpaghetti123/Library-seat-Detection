## Context

`ground-point-seat-matching`（已歸檔）把人的比對點改成接地點，並在離線評估工具中加入了立體框選與桌面優先判定：

- `calibrate.py --box`：依序點桌面的遠左、遠右、近右、近左四角，再點兩支前腳的落地點；後腳落點依遠近兩端的寬度比例推算。存成 `{"points": 外輪廓（凸包）, "top": 桌面四角, "floor": 地板投影四角}`。
- `detector.assign_layered()`：純函式，桌面優先、每個偵測只歸一席，已有單元測試。
- `scripts/evaluate_photos.py`：三種方法並列比較。

但實機路徑還沒接上：

- 後端 `PUT /api/seats/{label}/roi` 只接受剛好四點，存成 `{"points": [...]}`。
- `calibrate.py --box` 因此被限制只能 `--out` 存成本機 JSON。
- `detector.run()` 只取 `roi["points"]`，逐席呼叫 `classify_seat()`。

`seats.roi` 在資料庫是 JSON 欄位，結構可以直接擴充。

## Goals / Non-Goals

**Goals:**

- 立體框選的結果可以存進後端，並被實機偵測程式使用。
- 實機偵測預設使用桌面優先判定，解決前後排重疊造成的重複計入。
- 既有的四點 ROI 不需重新標定即可繼續運作。
- 保留逐席判定作為對照與回退選項。

**Non-Goals:**

- 不改資料庫 schema（不需要 migration）。
- 不做自動產生 ROI。
- 不微調 YOLO 模型；物品漏偵測（評估中剩餘錯誤的主因）另案處理。
- 不改前端：平面圖不顯示 ROI。
- 不加 ROI API 的管理者驗證（沿用現況，屬上雲前的安全性工作）。

## Decisions

### D1：ROI 結構沿用評估工具的格式

`seats.roi` 存成 `{"points": [...], "top": [...], "floor": [...]}`，`top` 與 `floor` 可省略。與 `rois.json`、`box_record()` 完全相同，評估、標定、偵測三處共用同一種格式，不需轉換。

舊資料 `{"points": [四點]}` 本身就是這個格式省略 `top`／`floor` 的特例，所以不需要資料轉移。

**替代方案**：另開 `roi_top`、`roi_floor` 欄位。捨棄原因是需要 migration，且三個欄位永遠一起讀寫，拆開沒有好處。

### D2：API 驗證規則

- `points`：3～16 點（凸包最多 8 點，留餘裕給手動多邊形）。
- `top`：若提供，必須剛好 4 點。
- `floor`：若提供，必須剛好 4 點，且必須同時提供 `top`。地板投影由桌面推算而來，單獨存在沒有意義。
- 座標必須是非負整數。

只驗證結構，不驗證幾何（例如桌面是否在外輪廓內）。幾何正確性由標定工具保證，API 端做幾何檢查的成本高，收益低。

### D3：判定模式 `--match {desk-first,per-seat}`，預設 `desk-first`

`desk-first` 呼叫既有的 `assign_layered()`：一個畫格只算一次，回傳所有座位的原始狀態。`per-seat` 為現行的逐席 `classify_seat()`。

四點 ROI 沒有 `top`，`assign_layered()` 會以整個外輪廓當桌面（`_region()` 的退回邏輯）。行為和逐席判定的差別只在「每個偵測只歸一席」：重疊時取中心最近的一席。對沒有重疊的舊標定，結果和逐席判定相同。

`--person-anchor` 只對 `per-seat` 有意義。`desk-first` 一律使用接地點：桌面優先的整個依據，就是「人的框底停在自己桌面」這個觀察。同時指定 `desk-first` 與 `--person-anchor center` 時，由 argparse 回報錯誤，避免使用者以為設定生效。

**替代方案**：把三種方法合併成一個 `--match {desk-first,ground,center}`。捨棄原因是 `--person-anchor` 已寫進 spec 與文件，改名會讓既有說明全部失效。

### D4：桌面優先對人也比對桌面，而不是地板投影

評估期間曾實作「人比對地板投影」：人的腳在地上，理論上比對地板較自然。但實拍中人坐在桌子遠側、面向鏡頭，下半身被桌子擋住，框底停在桌面遠端。後排的地板投影在畫面上正好位於前排桌面後方，結果前排的人被歸到後排。改成人也比對桌面後，這類錯誤消失。

`floor` 仍然保存：外輪廓由它推算，且未來改變相機角度（例如人坐在桌子近側、背對鏡頭）時，可能需要重新評估以地板判定。

### D5：多席符合時以桌面中心距離決定

退回比對外輪廓時，同樣以**桌面中心**而不是外輪廓中心計算距離。評估中曾用外輪廓中心，準確率比離線實驗低；原因是後排外輪廓往下延伸很長，中心被拉向前排。

### D6：標定工具寫入後端

`calibrate.py --box` 不加 `--out` 時，呼叫 `save_roi()` 送出完整的 `box_record()`。`fetch_existing_rois()` 改為保留完整結構，畫面上以 `roi_polygon()` 取外輪廓顯示。

## Risks / Trade-offs

- **[規則對評估資料過度擬合]** 桌面優先是看過同一批 24 張照片後才定的 → 另拍一組照片，只跑評估、不改規則，結果寫進 tasks 的驗證項目。
- **[相機角度不同時規則失效]** 若相機改從座位後方拍攝（人背對鏡頭），框底可能落在地上而非桌面 → 保留 `floor` 資料與 `per-seat` 模式，現場可切換；`--show` 畫出判定點與桌面方便診斷。
- **[座位偏坐時被歸給鄰座]** 評估中 B3 坐偏時被歸給 A2（2 次）→ 這是「只歸一席」的代價，比重複計入少；如需改善，可在標定時把桌面框得貼近實際使用範圍。
- **[ROI API 沒有驗證身分]** 任何人都能改 ROI → 沿用現況，列在上雲前的安全性工作。

## Migration Plan

1. 部署新後端：既有的四點 ROI 照常讀取。
2. 偵測程式更新後預設 `desk-first`；舊四點 ROI 只在重疊時行為不同。
3. 對有前後排重疊的場地，用 `calibrate.py --box` 重新標定。
4. 回退：偵測程式加 `--match per-seat` 即回到逐席判定，不需要動資料。
